## Verdict

**PASS on-chain, with one blocker for the REST payout path on testnet.** A two-milestone multi-release escrow in qUSD deploys through the REST API with the PLAN 10.1 roles, a plain SAC transfer to the escrow address funds it (so the deployed deal contract needs no change), the agent G key alone approves a milestone, the supplier receives the milestone minus a 0.3% protocol fee, and a disputed milestone is resolved back to Qafila. The REST API cannot build `release-milestone-funds` or `resolve-milestone-dispute` for a qUSD escrow because the Trustless Work fee address it fills in holds a USDC trustline only; those two steps were signed directly against the escrow contract by the same keys. **The fallback stays: `FF_TRUSTLESS_WORK=false` on testnet** (settlement is qUSD). On mainnet the settlement token is USDC, which the fee address holds, so the API path is expected to work there; untested.

## Findings

1. **Custom asset.** The API resolves `trustline: { address: <issuer G>, symbol }` to the SAC itself; the escrow was deployed with `trustline.address = CB7WLKU45...` (qUSD). But the API validates **every role wallet against Circle testnet USDC** (`GBBD47IF...`) before building `deploy` (receiver, platformAddress, ...) and `fund-escrow` (the funder), whatever the symbol says: `"The wallet for role 'receiver' does not have the required asset ... add the USDC asset"`. Adding an empty USDC trustline (0.5 XLM reserve, no USDC) to the supplier, admin and agent satisfied it (txs `e96fcfdc...`, `890a9e17...`, `32cae6ab...` at 18:10).
2. **Funding entry point.** `fund_escrow(signer, expected_escrow: Escrow, amount)` is only a `token.transfer(signer -> escrow)` plus a state check; the release precondition reads the escrow's token balance. A plain SAC transfer to the escrow contract address funds it (balance 30 after `transfer`, release succeeded). So **`pay_supplier_deposit` and `confirm_shipment` fund the escrow unchanged** when `terms.supplier` is the escrow address: no cross-contract call, no contract change (PLAN 10.1 question answered).
3. **Who signs.** Deploy: any funded G key (the agent; the deployer gets no role). Approve: the approver (agent). Release: the release signer (agent). Dispute: any role except the resolver (the agent as approver). Resolve: the dispute resolver (admin). The service provider never had to sign: `approve-milestone` worked on a milestone with status `pending` and empty evidence. Smart accounts cannot sign the API's transactions (classic G signatures), as PLAN 10.1 expected.
4. **Protocol fee and the blocker.** `release_milestone_funds(release_signer, trustless_work_address, milestone_index)` and `resolve_milestone_dispute(..., trustless_work_address, distributions)` take the fee address as a parameter on testnet; the API fills it with Trustless Work's account. The fee is **0.3% of every payout and of every resolution** (0.09 on 30, 0.21 on 70), taken from the receiver. Simulating the release with a fee address that has no qUSD trustline fails inside the SAC `transfer(escrow -> fee_addr, 900000)` (`Error(Contract, #13)`); with a fee address that holds qUSD it simulates fine with one auth entry (the release signer). The API masks that simulation failure as `400 Escrow not found` (an unapproved milestone correctly returns `The milestone must be completed to release funds`, so the lookup itself works). Conclusion: **through the REST API, payouts work only in assets the Trustless Work fee account holds (USDC, EURC)**. The direct calls in the table used the Qafila treasury as the fee address, which is fine for a spike but is not Trustless Work mode.
5. **Gross-up.** For the supplier to net the invoice, the deal raises `ceil(cost / 0.997)` (`escrowPlan` in `services/api/src/adapters/trustlesswork.ts`: gross cost, deposit = gross × deposit_bps floored like the contract, balance = the rest; the supplier nets at least the invoice). The difference is exposed as `escrow.fee` in `GET /deals/:id` and on the deal page.
6. **API shapes that differ from the skill files:** multi-release disputes are `POST /escrow/multi-release/dispute-milestone` and `resolve-milestone-dispute` (not `dispute-escrow` / `resolve-dispute`); there is no `/helper/set-trustline`; `get-escrow-by-contract-ids` wants `contractIds[]=`; `milestoneIndex` must be a string; amounts are numbers in token units; `send-transaction` returns `{ status, message, contractId, escrow }` for a deploy. `tx.hash()` is a `Uint8Array` in stellar-sdk 17 (wrap in `Buffer.from`).
7. **Indexer.** `/helper/get-escrows-by-signer` and `get-escrow-by-contract-ids?validateOnChain=true` showed the deploy, the direct funding (balance 30) and the approval flag within seconds, with `inconsistencyFound: false`.

## What this means for S2

- Implemented behind `FF_TRUSTLESS_WORK` (adapter live + mock, listing, agent release, dispute and resolve routes, deal page card). See `docs/PROGRESS-s2.md`.
- **Do not turn the flag on for the testnet demo**: the demo settles in qUSD and the API refuses to build qUSD payouts (finding 4). The deposit would sit in the escrow until ops disputes and resolves it by hand. Native payments stay the default (PLAN 3.2 fallback).
- To run the full path on testnet with the API: settle the deal in Circle testnet USDC (`SETTLEMENT_TOKEN_*` = USDC, every role wallet with a USDC trustline, funded from `faucet.circle.com`), or ask Trustless Work to add a qUSD trustline to their testnet fee account. Mainnet (USDC) should work as implemented; run one micro-deal first.
